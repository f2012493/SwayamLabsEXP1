# Prediction: zero-shot pick-and-place in simulation (pre-registered 2026-10-15)

Written and committed **before any attempt was run**. The git commit date is the
proof. Do not edit this file after the data exists; results go in
`studies/out/sim_pick_place_zero_shot.md` and link here.

## What is being measured

ROADMAP Phase 0 step 4, in simulation first: Claude drives the arm zero-shot through
the `swayam-arm` MCP tools on the instruction

> Move the cube from the bed into the tray slot and stop when the verifier passes.

Scene: `sim/so101/scene_task.xml` (20 mm cube spawned on the bed at a seeded
position, ±25 mm, yaw ±20°; kit-tray slot with a 22 mm pocket, 1.5 mm lead-in and
8 mm funnel). Verifier: `is_cube_in_slot` (cube centre within 3 mm of the slot
centre, moving < 5 mm/s, released). The grasp is a labelled weld (no grasp physics);
what this measures is planning, precision and judgment of when to stop, not grasping.

## Protocol (fixed before the run)

- 10 attempts, cube seeds 0–9, in order, none dropped. Any attempt that fails for an
  infrastructure reason (server crash, CLI error, timeout) is still counted as a
  failure and flagged in the table.
- Each attempt is a fresh `claude -p` conversation (model `claude-fable-5-1`; the
  exact id used is recorded from the CLI output) started in an empty directory: no
  CLAUDE.md, no source code, no built-in tools; only the 10 `swayam-arm` MCP tools,
  with the independent safety hook attached. Max 60 turns, 15 min, $10 per attempt.
- Each attempt starts its own MCP server (`SWAYAM_SCENE=task`, `SWAYAM_CUBE_SEED=k`)
  so nothing carries over. The server logs every tool call with the post-call scene
  and verifier state to `runs/` under `run_tag = zero-shot-<stamp>-<k>`.
- Scoring is recomputed from `runs/` by `swayam.experiments.zero_shot`, never from
  the subject's own report. Success = the verifier state after the **last** tool call
  of the attempt is true.
- The scripted rehearsal (`tests/test_task_scene.py::test_scripted_pick_and_place_passes_the_verifier`)
  shows the task is solvable with these tools in 9 commands.

## Predictions

| Quantity | Prediction |
|---|---|
| Successes over 10 attempts | **7 / 10** (Wilson 95%: 40–89%) |
| Median MCP tool calls per attempt | **14** |
| Most likely failure mode | **Cube released with its yaw outside the funnel's ±20° capture** (the cube turns ~58° with the shoulder pan between bed and tray; the subject must correct with wrist roll and read the cube yaw back before releasing). The cube ends up resting on the funnel, 8–12 mm above the slot centre. |
| Second failure mode | Descending with the gripper less than ~70 % open or more than 15 mm off the cube, so no grasp happens, then running out of turns while hunting. |
| Attempts that keep commanding motion after the verifier first passes ("refine past success") | **at most 1** |
| Irrecoverable events (cube off the table) | **0** |
| Attempts that end without ever calling the verifier | 0 |

Reasoning: the hard physical part (grasp) is a weld, so success turns on three
things a careful operator can get right from the numbers alone: open wide enough,
aim the TCP at the cube centre, fix the yaw before releasing. The AA-Robotics finding
that models judge task completion poorly is the part I expect to see: I expect the
subject to call the verifier and stop, because the instruction names it, but not
reliably.

## Decision rule

- **Success-rate prediction holds** if measured successes are in **[5, 9]** of 10.
- **Tool-call prediction holds** if the median is in **[8, 25]**.
- **Failure-mode prediction holds** if, among failed attempts, the modal final state
  is "cube resting on or near the funnel with |yaw mod 90°| > 20°" (from the logged
  final cube pose), or there are no failures.
- If successes < 5: the first suspect is the tooling, not the model. Before changing
  anything, read every `refused` and `aborted` record; if more than half of the
  failures involve a refused or aborted move, the next prediction is about a tooling
  fix, not about the model.
- If successes ≥ 9: the simulated task is too easy to be a useful baseline; the next
  version removes the weld's 15 mm forgiveness or shrinks the funnel, with a new
  prediction.
- Whatever happens, the same instruction and seeds are rerun on hardware in Phase 0
  step 4, with this file as the sim reference.
